# BITACORA 23/10/2025

Resumen

### Estructura de Branches

- El sistema utiliza branches individuales que deben enviarse al departamento correspondiente para revisión
- Cada usuario debe crear su branch individual para sus actividades
- Se debe crear una branch temporal separada por cada actividad, no agrupar múltiples actividades en una sola

### Proceso de Revisión

- Una vez creada la branch individual, se debe enviar al departamento para revisión
- El departamento revisa y acepta el pull request si está correcto
- Si hay problemas, será necesario modificar y enviar nuevamente

### Convenciones de Nomenclatura

- Es importante seguir la estructura de nomenclatura establecida
- Las branches deben incluir el prefijo "TEP" para poder ser aceptadas en Stage
- Las que tengan "PA" no pueden ser aceptadas por recuerdo en ningún lado
- El formato incluye: Departamento, prefijo (TEP), descriptivo IDE, y sufijo individual
- Stage es el "último átomo corriendo" y no lleva punto ni número de Stage

### Permisos y Aprobaciones

- Solo los propietarios de departamentos pueden aceptar pull requests en sus departamentos
- Todos los stages necesitan una aprobación
- Los departamentos también requieren aprobación
- Cada participante ya está asignado como dueño de su respectivo departamento

# BITACORA 28/10/2025

Resumen

### Cambios en Requerimientos Funcionales

- Se acordó simplificar los requerimientos funcionales para hacerlos más específicos y mejor organizados
- Se redujo la lista eliminando requerimientos redundantes como "Automatically calculate and display remaining rental time" que ya está incluido en "Register and manage local renters"
- Los principales requerimientos funcionales ahora son: registro y administración de renta de lockers, aplicación de descuentos, gestión de ventas de productos y operaciones financieras

### Nuevo Enfoque de Abstracción del Proyecto

- Se decidió restructurar el proyecto alrededor de "tickets" en lugar de clientes
- Se rediseñó el diagrama de clases para incluir Ticket, Servicio, Renta y Venta
- Cada ticket puede tener múltiples servicios (ventas o rentas) asociados
- Se discutieron los atributos necesarios para cada clase: ID, tipo de servicio, nombre, total, descuento, etc.

### Reorganización Departamental

- Se creó un nuevo departamento de Diseño
- Se modificaron los IDs de todos los departamentos: A-Proyecto, B-Producto, C-Requerimientos, D-Proceso, E-Diseño, F-Presentación
- Se eliminó el departamento de competencias y sus tareas fueron absorbidas por el departamento de proceso

### Documentación y Artefactos

- Es necesario que cada requerimiento funcional tenga su propio archivo con documentación detallada
- Se requiere crear historias de usuario, criterios de aceptación y casos de uso
- Se debe implementar código usando el patrón MVC (Modelo-Vista-Controlador)
- Se debe asegurar la correspondencia entre el código y los requerimientos funcionales

### Interfaz de Usuario

- Se mostró el diseño de interfaz con tres componentes principales: creación de tickets, manejo de rentas y reportes de servicios
- La interfaz permite visualizar el estado de los lockers (disponible/ocupado), información del cliente y tiempo acumulado
- Los tickets pueden incluir múltiples servicios y rentas, con opciones para añadir más elementos

### Planeación de Presentación

- Se propuso un formato de entrevista para el video de presentación, enfocado en los problemas y soluciones del proyecto
- El video debe incluir información sobre los cambios en el equipo, reducciones del alcance y ajustes realizados
- La duración debe ser de 5 minutos
